## Product OS (V1) — local learning harness

This folder materializes the repository structure described in
`../product_os_learning_harness_v1_prd_tdd_v2.md`.

### Quick start

- Add evidence files under `evidence/` (start with `evidence/agent-builders/_inbox/`).
- Keep raw evidence in the `## Raw evidence` section; keep your commentary in `## Notes`.
- Use the scripts to create consistent files and validate metadata.

### Commands

From the `product-os/` directory:

```bash
PYTHONPATH=src python3 -m product_os.cli new-evidence --domain agent_builder --source_name "Notion Custom Agents" --slug notion --title "Hands-on: first agent" --source_type hands_on --product_area getting_started

PYTHONPATH=src python3 -m product_os.cli validate
PYTHONPATH=src python3 -m product_os.cli build-index

# End-to-end: extract + render living outputs from beliefs/
PYTHONPATH=src python3 -m product_os.cli refresh

# Record hashes for new evidence (append-only immutability ledger)
PYTHONPATH=src python3 -m product_os.cli lock
```

Living insights/hypotheses are edited in `beliefs/` (not in `outputs/`).
`outputs/` is a deterministic render. Mechanical per-evidence extracts go to
`derived/raw-synthesis/` and must not be treated as insights.

If you have a working `pip`, you can optionally install an executable:

```bash
pip install -e .
product-os validate
```

### Where to put observation-matrix notes

- Working notes (not treated as raw evidence):
  - Index: `notes/agent-builders/observation-matrix-notes.md`
  - Per-product matrices: `notes/agent-builders/matrix/`
- If you want those notes to participate as evidence, copy the relevant parts into a normal evidence file in `evidence/agent-builders/<product>/`.

### Immutable evidence vs living scorecards

Evidence files are **append-only**: one per source or pass, never
rewritten to reflect a newer opinion. Competitor scorecards are the
opposite — **overwrite in place** to hold the current read.

- Immutable: `evidence/competitors/<slug>/ev-comp-<slug>-00N.md`
- Living: `notes/competitors/scorecard/<slug>.md`
- Convention and status vocabulary: `notes/competitors/scorecard/_scorecard-guide.md`

Every scorecard row carries a status (`VERIFIED` / `DOCS` / `CLAIMED`
/ `UNSEEN` / `DISPUTED`) plus the evidence IDs behind it, so vendor
marketing never silently becomes a product fact. When a status
changes, add a Changelog line.

Loop for a new source:

1. Create the evidence file (immutable).
2. Edit the affected scorecard rows + `effective_date` + Changelog.
3. If a cross-cutting belief moved, edit `beliefs/`.
4. `refresh`, then `lock`.

#### This is enforced, not just documented

`validate` (and `refresh`) fail on:

- a locked evidence file that was modified, renamed, or deleted;
- a competitor with evidence but no scorecard;
- a scorecard that does not cite every evidence ID for its competitor
  (this is what forces the update when evidence is added);
- a scorecard citing an evidence ID that does not exist;
- a status outside the vocabulary;
- a missing `## Changelog` or incomplete scorecard frontmatter.

`evidence-lock.json` is the immutability ledger. New files are added
automatically by `lock`; modifications are refused unless you pass
`--accept`, which is for genuine corrections (typo, bad citation) and
should be recorded in the Changelog — not for rewriting an
interpretation.

Implementation: `src/product_os/corpus_rules.py`. Agent-facing version:
`.cursor/rules/corpus-contract.mdc`.

### Readouts

`decks/` holds hand-maintained HTML readouts for presenting — single
file, no dependencies, prints to PDF. Not generated by `refresh`, so
re-read `beliefs/` before presenting one again. Copy the most recent
as the template; keep the status pills, the evidence citations, and
the "what we do not know" callouts.

Harness debt and deferred work: `notes/backlog.md`.
